# Interview Notes

## Project Positioning
FitMind AI is positioned as a training log plus a deterministic calculation layer, with future room for evidence-traceable AI suggestions.

The key idea is that the product should not behave like a generic chat wrapper. It should first own trustworthy training data, compute reproducible signals from that data, and preserve traceability so any future higher-level suggestion can point back to the workouts and sets that justified it.

In interview terms, the product pitch is:
- a workout tracker that stores real training history
- a backend calculation layer that produces deterministic training summaries
- an evidence model that makes future suggestions inspectable instead of opaque

## Why The Project Does Not Start With AI Chat
The project intentionally does not start with AI chat because chat alone would create a weak foundation. If the system cannot first answer basic questions such as "what was trained," "how much volume was done," or "how one exercise changed over time" in a deterministic way, then any LLM-generated guidance would be hard to validate.

Starting with the calculation layer provides several benefits:
- the derived numbers are testable
- the API behavior is easier to debug than prompt-only behavior
- trust is higher because outputs can be tied to stored evidence
- later AI features can consume stable inputs rather than inventing calculations at runtime

This makes the architecture "deterministic before generative," which is a stronger engineering story in an interview.

## Phase 1 Value: Training Log CRUD
Phase 1 established the core training log workflow:
- register and login
- memory-only auth for the MVP
- search and select exercises
- create workouts with sets
- list workouts
- inspect workout detail
- delete workouts

The value of Phase 1 is not just CRUD for its own sake. It proves that the app owns first-party training data with authenticated user boundaries. Without that layer, later analytics or AI explanations would have no reliable source of truth.

## Phase 2 Value: Deterministic Calculation Layer
Phase 2 adds readonly calculation APIs on top of the existing workout data without changing workout CRUD contracts or the database schema.

### `GET /api/training/summary`
This endpoint returns a user's readonly range summary. It answers:
- how many workouts were included
- how many sets were included
- how many reps were accumulated
- how much total volume was accumulated
- which exercises contributed most within the requested range

### `GET /api/training/exercise-progress`
This endpoint returns a readonly progress view for one exercise in a requested range. It answers:
- how many workouts included that exercise
- how many matching sets were included
- total reps and total volume for that exercise
- max observed weight in range
- approximate best estimated 1RM in range
- per-session rollups for recent inspection

The important architectural point is that both endpoints sit behind auth, derive the user from auth context, and compute results on the server from stored workouts and sets.

## Evidence Design
One of the most interview-worthy parts of the project is the evidence model.

The calculation responses include:
- `workout_ids`: which workouts contributed to the aggregate
- `set_ids`: which sets contributed, especially for exercise progress
- `calculation_rules`: plain-text rules describing how the numbers were computed

This matters because future suggestions should be explainable. Instead of saying "the AI thinks your bench is improving," the system can eventually say "this suggestion is based on these workouts, these sets, and these deterministic rules."

That creates an audit trail between raw training logs, backend calculations, and any later interpretive layer.

## Why The Date Range Uses A Half-Open Interval
The API accepts inclusive calendar inputs like `start_date=YYYY-MM-DD` and `end_date=YYYY-MM-DD`, but internally filters timestamps with a half-open interval:
- `performed_at >= start_date::date`
- `performed_at < (end_date::date + interval '1 day')`

This is a standard backend safety pattern. It prevents off-by-one errors near the end of a day and avoids fragile logic around `23:59:59.999...` boundaries. It also preserves the user's mental model that the selected end date should be included.

## Why `estimated_1rm` Is Approximate
The exercise-progress endpoint exposes `estimated_1rm_kg` using the Epley formula:

`estimated_1rm_kg = weight_kg * (1 + reps / 30)`

This is explicitly an approximate signal, not a prescription and not a guaranteed real one-rep max. In interview terms, the project treats this as a useful comparative metric for trend inspection, not as medical advice or coaching certainty.

That distinction is important because it shows responsible product framing and avoids overstating what a simple deterministic formula can prove.

## Why The Frontend Panels Are Readonly In Phase 2
The summary and progress panels are readonly by design in Phase 2.

That choice keeps the batch focused on calculation correctness instead of UI complexity. The frontend panels are responsible for presenting deterministic outputs, handling loading and empty states, and refreshing when workout data changes. They are not yet trying to be full analytics workbenches with charts, date controls, or recommendation flows.

This scope control keeps the architecture clean:
- backend owns calculation logic
- frontend presents stable readonly results
- workout CRUD remains the source of mutations

## Create/Delete Refresh Behavior
The refresh behavior is intentionally simple and explicit.

When a workout is created successfully:
- the workout list refreshes
- the training summary refreshes
- the exercise progress panel refreshes only if an exercise is currently selected

When a workout is deleted successfully:
- the workout list updates
- the training summary refreshes
- the exercise progress panel refreshes only if an exercise is currently selected

This is a good interview talking point because it shows the UI is reactive to mutations without introducing a more complex state-management or routing layer.

## Current Non-Goals
The current project state explicitly does not include:
- AI chat
- Tool Calling
- SSE
- RAG
- MCP
- Agent orchestration
- charts or reports
- coaching recommendations

These are not accidental omissions. They are scope boundaries that protect the deterministic layer from being diluted before the core data and evidence model are solid.

## Interview Q&A

### How is this different from a normal workout tracker?
A normal workout tracker often stops at storing logs and displaying historical entries. FitMind AI is being structured to go one step further: it adds a deterministic calculation layer and an evidence model so future suggestions can be tied back to concrete workouts and sets. The differentiation is not "it has AI"; the differentiation is "it creates traceable training intelligence on top of owned data."

### Why not calculate everything in the frontend?
The calculations live in the backend because they are part of the product contract, not just presentation. Server-side calculation improves consistency, keeps user isolation enforcement close to the data, avoids duplicated logic across clients, and makes future consumers like AI layers or other clients reuse the same deterministic results.

### Why not let an LLM directly summarize the logs?
An LLM can be helpful later, but it should not be the first source of truth for arithmetic or filtering. If the model summarizes raw logs directly, it becomes harder to verify accuracy, harder to test regressions, and harder to explain why a conclusion was reached. The current design makes the LLM a future interpretation layer on top of deterministic results, not a replacement for them.

### What is the future Tool Calling plan?
The long-term idea is that future AI features could call stable deterministic endpoints or equivalent calculation services as tools. That would let a model explain or synthesize training insights while still grounding the answer in traceable evidence. Importantly, that is only a future direction. Tool Calling is not part of the current delivered scope.

### How is user isolation guaranteed?
User isolation is enforced through authenticated backend context. The calculation endpoints do not accept a user id from the client. Auth middleware resolves the user, and repository queries filter workouts by that authenticated user before aggregating anything. This reduces the risk of cross-user data leakage and keeps access control server-owned.
